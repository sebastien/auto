# Plan

## Purpose

We want to define how tasks can be organised in a plan. While upfront planning
based on a goal is possible in theory, in practice the initial plan needs to
be refined, and sometimes even changed based on discoveries during task
execution. Our approach to planning, which is the elaboration of tasks and
their sequencing based on dependencies, needs to take the following into
consideration:

- *Elaboration*: given a goal ("I want to do THIS"), propose the tasks to
  deliver it, independently of any workflow.
- *Readiness*: determine if a task is ready to be run, which depends on its
  input availability and open gaps.
- *Budget*: tasks draw from a token, time or monetary budget allocated to the plan.
- *Failure*: tasks can fail, from system or tool errors, from bad input, bad
  output or from running out of budget.
- *Recovery*: a failed task may be retried, or aborted and reworked,
  potentially leading to a replanning.
- *Gaps*: missing inputs, genuine questions (gaps in instructions or data),
  decisions to be made and approvals are tracked until resolved.
- *Learnings*: execution, failures and decisions lead to findings (surprises,
  recurrent questions, edge cases, patterns) that inform planning and
  execution.

The plan holds the structure and state; decisions about sequencing, retries
and budget enforcement belong to Orchestration.

## Conceptual Model

Plan: the scope and state of a set of tasks working towards a goal.
- `id`: identifier
- `goal`: text describing the intended outcome, the goal of the root task
- `inputs`: data and assets given to the plan, available to its tasks
- `root`: the root task, defined by `tsk/root.md`, whose success is the plan
  success
- `tasks`: tasks, with their plan facet, all descending from the root task
- `gaps`: Gaps raised within the plan
- `budget.{tokens,cost,time}`: total budget, drawn from by task runs
- `usage.{tokens,cost,time}`: sum of the usage of all runs in the plan
- `learnings`: references to the learnings informing the plan
- `revision`: id of the latest PlanRevision
- `journal`: PlanRevisions, append-only
- `status`: `Draft`, `Active`, `Succeeded`, `Failed` or `Abandoned`

Task (plan facet): attributes added to a task within a plan.
- `state`: derived: `Open` (has open gaps), `Blocked` (input tasks or
  children not succeeded), `Ready`, or the status of its latest run
- `attempts`: number of runs
- `replaces`: id of the task it reworks, if any
- `parent`: id of the task it was decomposed from; `root` by default, none
  for the root task
- `children`: derived: ids of the tasks whose `parent` is this task

Root task: the task defined by `tsk/root.md`, with the reserved id `root`.
- Its goal is the plan goal, and its inputs are the plan inputs
- Its children are the tasks elaborated from the plan goal
- Its Post and Evaluation, if any, are the definition of done of the plan
- Like any aggregate, it may omit its Process (see Aggregates)

Gap: something a task or plan needs and does not have.
- `id`: `{timestamp}-{random}`, generated by Auto
- `plan`: plan reference (see References)
- `kind`: `input` (missing input), `information` (gap in instructions or
  data), `decision` (choice to be made) or `approval` (human sign-off on
  pinned content)
- `subjects`: `[{ref,digest}]`, the pinned content the gap is about; required
  for `approval`
- `question`: what is needed
- `options`: possible answers, if any
- `concerns`: optional labels of what the answer affects across the project
  (eg. `architecture`, `experience`, `data`), free-form
- `raised_by`: an Elaborator run, a run (eg. a script question) or a human
- `needed_by`: task ids (`root` for the plan)
- `status`: `Open`, `Resolved` or `Dismissed`
- `decision`: the Decision resolving it
- `revision`: id of the PlanRevision raising it, generated before writing

Decision: a choice made by a human or a run: the resolution of a gap, or a
decision made directly (eg. settled in conversation). Decisions are project
knowledge: they must be recorded wherever they are made.
- `id`: `{timestamp}-{random}`, generated by Auto
- `plan`: plan reference (see References)
- `gap`: gap id, when it resolves one
- `question`: what was decided, when there is no gap
- `answer`: a Value (see [Script](spec-002-script.md))
- `rationale`: text
- `concerns`: labels of what it affects, defaulting to the gap's; decisions
  are project knowledge that outlives the plan (see
  [Memorisation](spec-010-memorisation.md#decisions))
- `author`: a human or a run
- `source`: where it was made, when not through a gap (eg. a conversation
  and time, `auto-agent:conversation/{id}@{time}`)
- `date`: datetime
- `revision`: id of the PlanRevision recording it, generated before writing

PlanRevision: an entry in the plan journal, describing operations rather than
content.
- `id`: `{timestamp}-{random}` (eg. `20261105T101230Z-3f9a`), generated
  before any write
- `seq`: position in the journal, assigned at append
- `author`: an Elaborator run, or a human
- `date`: datetime
- `reason`: text, and the run, gap or learning that triggered the change
- `operations`: list of
  - `add(task,digest,parent?)`, `remove(task)`, `replace(old,new,digest)`
  - `edit(task,digest)`, for tasks without runs
  - `raise(gap)`, `resolve(gap,decision)`, `dismiss(gap)`
  - `record(decision)`, for a decision made without a gap
  - `update(field)`, for the plan goal, inputs or budget (the root task
    definition)

A `digest` pins the content of a reference (see Digest), so that pinned
references (eg. from a gap or a decision) can be verified.

## Elaboration

Elaboration decomposes the goal of a task into its children. It is done by
an Elaborator, a baseline meta-task provided with the plan: an ordinary task
(see [Task](spec-003-task.md)). Creating and refining a plan are elaborations
of the root task:

| | Creation | Refinement | Decomposition |
|---|---|---|---|
| Task | Root | Root | A task of the plan |
| Inputs | Goal, plan inputs, learnings, available scripts and assets | Same, plus the plan state (task states, outputs, gaps, failures) and the reason | Same as refinement |
| Output | Children and gaps | Children added, removed or replaced, and gaps | Same as refinement |
| Applied as | The first revision | A new revision | A new revision |

Elaborated tasks only reference inputs that are plan inputs, available scripts
and assets, or outputs of other tasks (`task:{id}`). Inputs that cannot be
resolved are raised as gaps rather than invented.

The Elaborator interface, the TaskElaboration format and the framework are
defined in [Elaboration](spec-006-elaboration.md).

### Aggregates

A task with children is an aggregate:
- It remains responsible for its output, and runs once its children have
  succeeded, with their outputs as the `children` input.
- It may omit its Process: its run then succeeds without a model call, with
  the outputs of its children as output, and its Post and Evaluation still
  apply.
- Decomposing it does not edit its definition, so references to it remain
  valid and it may be decomposed again after a failure.

## Storage

Operational state is owned by Auto, knowledge and provenance by Memo:

| Element | Stored in | Notes |
|---|---|---|
| Plan, Task, Run | Plan directory | Operational state |
| PlanRevision | Plan directory | Append-only journal |
| Gap, Decision | Memo | Referencing plan elements with pinned `{ref,digest}` |
| Learning | Memo | See [Memorisation](spec-010-memorisation.md) |

Memo is the default storage integration, not part of the model. Record formats,
identity mapping and consistency rules are defined by the
[Memo integration](spec-005-memo.md).

## Format

A plan is a directory, acting as the scope of its tasks, stored in the
project as `.auto/{plan}/`, next to the project catalogue (see
[Elaboration](spec-006-elaboration.md)). The project's `.auto/` is a Memo store
(see [Memo integration](spec-005-memo.md)) in which each plan is a namespace:
its definitions and knowledge records are Memo documents grouped by
three-letter kinds, while its runs and logs are plain files beside them, which
Memo does not scan.

```
.auto/{plan}/
  tsk/root.md         # Root task: the goal (description), inputs and budget (frontmatter)
  tsk/{task}.md       # Task definitions (see Task)
  gap/{id}.md         # Gaps, then decisions, as Memo documents (see Memo integration)
  dec/{id}.md
  runs/{run}/         # Output, journal and receipt (see Task)
  journal.jsonl       # PlanRevisions, one per line
  events.jsonl        # PlanEvents, one per line (see Orchestration)
```

```markdown
---
budget: {tokens: 500000, cost: 5.00, time: 2h}
elaborator:
  task: auto:catalogue/task/elaborate
  budget: {tokens: 100000, cost: 1.00, time: 20m}
inputs:
  changelog: ./CHANGELOG.md
---
Publish release notes for version 2.0

## Post

Optional definition of done of the plan.
```

- `tsk/root.md` uses the task format (see Task), whose description is the plan
  goal, stated once. The directory name is the plan id, while the root task
  id is always `root`; `budget` is the plan budget, which the root task runs
  draw from like any other run. Fields that are empty or derivable (an empty
  `inputs`, a `goal` equal to the description) are not written.
- Task ids start with `tsk-` (eg. `tsk-build-site`), except the root task's
  reserved `root`. Auto adds the prefix to a task created without it, and
  accepts either form wherever a task is named (eg. `task:build-site` and
  `task:tsk-build-site` are the same reference), so Elaborators and humans may
  omit it. A definition file is named after its id without the prefix, which
  its `tsk/` folder states (eg. `tsk/build-site.md`); its `id` field keeps the
  full id.
- Generated ids also start with a three-letter code naming their kind: `pln-`
  for plans, `run-` for runs (named after their task without its prefix, eg.
  `run-build-site-20261105T1012-01`), `rev-` for revisions, `gap-` and `dec-` for gaps and
  decisions, `cnt-` for continuations and `asm-` for budget assessments (eg.
  `rev-20261105T101230Z-3f9a1c2e`).
- `PlanCreate` names a plan `pln-NNN-slug`: `NNN` is an incremental number of
  at least three hex digits, kept in `.auto/.counter` and skipping numbers
  already used; `slug` is up to four significant words of the goal's first
  sentence (articles, conjunctions, pronouns and generic verbs such as
  "create" are dropped), at most 32 characters, never cut mid-word.
- A plan may be selected by its id or by its number alone (eg. `--plan 00a`
  or `--plan pln-00a`), when exactly one plan has that number.
- Task ids are unique within the plan, and `root` is reserved.
- Tasks may reference scripts and assets outside the plan by `PATH`.

### References

Plan elements are referenced with `PATH` schemes (see Script). Inside a plan,
shorthand schemes resolve within the plan; the canonical form is used from
anywhere else (eg. Memo records, APIs):

| Target | Inside a plan | Canonical |
|---|---|---|
| Plan | — | `auto:{plan}` |
| Plan input | `plan:{name}` | `auto:{plan}/input/{name}` |
| Task output (latest succeeded run) | `task:{id}` | `auto:{plan}/task/{id}` |
| Task definition | `task:{id}/definition` | `auto:{plan}/task/{id}/definition` |
| Materialized companion source | `task:{id}/source/{hash}` | `auto:{plan}/task/{id}/source/{hash}` |
| Root task (output, definition) | `task:root`, `task:root/definition` | `auto:{plan}/task/root`, `auto:{plan}/task/root/definition` |
| Run output | `run:{id}` | `auto:{plan}/run/{id}` |
| Run receipt or journal | `run:{id}/receipt`, `run:{id}/journal` | `auto:{plan}/run/{id}/{part}` |
| Plan revision | `revision:{id}` | `auto:{plan}/revision/{id}` |
| Gap | `gap:{id}` | `auto:{plan}/gap/{id}` |
| Decision | `decision:{id}` | `auto:{plan}/decision/{id}` |
| Catalogue entry | — | `auto:catalogue/{kind}/{name}` (see [Elaboration](spec-006-elaboration.md)) |

Task, run, gap and decision ids contain no `/`, so `/{part}` is unambiguous and `#` remains
available for ranges and symbols. Plan ids `catalogue` and `agent` are reserved:
`auto:agent/{id}` references memorisation agents and their consolidation runs
(see [Memorisation](spec-010-memorisation.md)).

A materialized companion source belongs to its task definition and is available
without a succeeded task output, including after removal through the archived
definition. Its 64-character lowercase hex identity hashes the original source
location and compiled document, so different inclusion scopes can coexist.
Its content digest is computed over the exact compiled document bytes; the
original source reference/digest and source-relative location remain recorded.

Removing a task retains its final definition bytes. Definition references still
resolve those bytes with the same digest and original relative-reference origin.
The task remains absent from the current plan and cannot be started or have its
id reused. A definition reference is an asset; unlike an output reference, it
does not require a succeeded run of the referenced task.

### Digest

A digest is `sha256:{hex}`, supplied by the owner of the referenced content:
- Plan elements: computed by Auto over the exact bytes of the file (task
  definition, run output, receipt or journal). For a plan revision,
  over the bytes of its JSONL line, without the newline.
- Local files and assets: computed by Auto over the exact bytes of the file.
- Storage entries (eg. Gaps, Decisions, `memo:` references): the revision
  given by the storage integration (see [Memo integration](spec-005-memo.md)).

## Operations

Plan:
- `PlanCreate(context,goal,inputs?,budget?,effects?,agents?)`: creates the plan and its root
  task, and elaborates the root task, producing the first revision.
  `effects` records explicit human requests as grants (see Plan Policy).
- `PlanGet(context,id)`: returns a plan.
- `PlanList(context,filter?)`: lists plan summaries (id, status, goal, task
  and gap counts, hold, usage, `created` and `updated`), filtered by field.
  Dates are derived, not stored: the earliest and latest of the revision
  dates, run start and end times, and the root task's modification time.
  Unreadable plans are
  listed as `Unreadable` with their error rather than failing the list.
- `PlanRefine(context,plan,reason,task?)`: elaborates the task (by default
  the root task) on the current state, applying the result as a new revision.
- `PlanRevise(context,plan,changes,reason)`: applies a manual revision.
- `PlanReady(context,plan)`: returns the tasks ready to run, extending
  `TaskReady` with the open gaps check.
- `PlanStatus(context,plan)`: returns progress, open gaps, budget and failures.
- `PlanJournal(context,plan,since?)`: returns the revisions, optionally since
  a given revision.
- `PlanAbandon(context,plan,reason)`: ends the plan as `Abandoned`.
- `PlanRepair(context,plan)`: reconciles the journal with the Memo records
  (see Repair).

Gap:
- `GapRaise(context,plan,gap)`: raises a gap, returning its id.
- `GapList(context,plan,filter?)`: lists gaps, filtered by status, kind or task.
- `GapDecide(context,gap,answer,rationale)`: resolves a gap, returning
  a Decision.
- `GapDismiss(context,gap,rationale)`: dismisses a gap as no longer relevant.

Decision:
- `DecisionRecord(context,plan,question,answer,rationale,concerns?,source?)`:
  records a decision made without a gap, returning it. Its author is the
  context's author.

Events, recorded in the plan event log (see
[Orchestration](spec-009-orchestration.md)) and, when a run is concerned, in
its journal:
- `GapRaised(gap)`: a gap was raised.
- `GapResolved(gap,decision)`: a gap was resolved.
- `DecisionRecorded(decision)`: a decision was recorded without a gap.

## Rules

- *Scope*: a task belongs to a single plan, which holds its state and runs.
  Running a task (`TaskStart`) is done in the context of its plan.
- *Readiness*: a task is `Ready` when it has no open gaps and all its input
  tasks and children have a succeeded run. Preconditions are checked when the run starts
  (see Task lifecycle).
  An output gate additionally requires a human's affirmative decision for the
  exact current output digest, or an explicit human dismissal with a rationale.
  Rejection resolves the gap but keeps dependents blocked and leaves the
  producing run `Succeeded`. A retry or rework produces a new output requiring
  its own gate; an earlier decision cannot approve that output. These rules
  also apply to dependents added after the producing run.
- *Gaps*: a question raised during a run (`ScriptQuestion`) is raised as
  a gap; the run is `Waiting` until a decision is made, and the answer is
  passed back to the run.
- *Answers*: a run of a task is given the question, answer and rationale of
  every resolved gap that lists the task or one of its ancestors in
  `needed_by`, except approvals, ahead of its process. An Elaborator run is
  given those of the task it elaborates, so a decomposition neither asks again
  nor loses an answer. Tasks do not reference gaps in their inputs.
- *Revisions*: every change to the plan, its tasks or its gaps appends
  a revision to the journal. The journal order is authoritative; the current
  revision is the last entry.
- *Single writer*: journal appends are serialised (eg. a lock file on the plan
  directory). Repair runs under the same lock.
- *Write order*: the revision id is generated first, then Memo is written,
  then the journal is appended:
  - Raise: write the Gap (with the revision id), then append `raise(gap)`.
  - Resolve: write the Decision (with the revision id), update the Gap status,
    then append `resolve(gap,decision)`. A `Waiting` run resumes only after
    the append.
  - Record: write the Decision (with the revision id), then append
    `record(decision)`.
- *Decisions*: may be recorded on any plan, including an ended one: a
  decision changes no task or status, and is project knowledge that outlives
  the plan. Recording one on an ended plan does not reopen it.
- *Repair*: keyed by gap id. Gaps of the plan found in storage without
  a matching `raise`, or resolved without a matching `resolve`, have the
  missing entry appended, reusing the revision id stored with them. A gap id is
  never raised or resolved twice in the journal. Decisions without a gap found
  in storage without a matching `record` have it appended, keyed by decision
  id. Repair runs before any journal
  write, and on `PlanRepair`. Storage-specific cases (eg. partial resolution)
  are defined by the integration (see [Memo integration](spec-005-memo.md)).
- *Immutability*: a task with runs is never edited; changing it is a rework
  (a new task that `replaces` it). Tasks without runs may be edited in place,
  their new digest recorded in the revision. Runs, decisions and the journal
  are append-only; gaps are never deleted, only their status and decision
  change.
- *Recovery*: a retry is a new run of the same task; a rework is a new task
  that `replaces` the failed one; a redecomposition reworks the children of
  a failed aggregate; a replan is a refinement. All are recorded as revisions,
  except retries which are recorded as runs.
- *Decomposition*: decomposing a task does not edit it, so it applies to
  tasks with runs (see Aggregates). Children are added with `parent`, and
  removing a parent removes its children. The root task cannot be removed or
  replaced.
- *Budget*: the plan usage is the sum of its runs usage, compared to the
  plan budget.
- *Status*: a plan is `Draft` until a task is run, and `Succeeded` when its
  root task has succeeded, which implies all its tasks have succeeded.
