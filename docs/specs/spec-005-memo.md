# Memo Integration

## Purpose

We want to define how Auto stores knowledge and provenance in
[Memo](https://github.com/sebastien/memo), its default storage integration
(see [Structure](spec-001-structure.md)). Memo provides the primitives
(entries, identity, properties, revisions, pinned references, queries); Auto
owns the record formats, semantics and validation. The integration needs to
cover:

- *Mapping*: how Gaps and Decisions (see [Plan](spec-004-plan.md)) are
  represented as Memo entries
- *Identity*: how Auto references resolve to Memo entries
- *Digests*: how pinned references work across both systems
- *Consistency*: write order and repair, given that Memo has no atomicity
  across entries

## Conceptual Model

| Auto element | Memo entry | Identity |
|---|---|---|
| Gap | Document, kind `gap` | `auto:{plan}/gap/{id}` |
| Decision | Document, kind `decision` | `auto:{plan}/decision/{id}` |

- The Memo `identity` is the canonical Auto reference (see Plan references),
  so Auto references resolve to Memo entries without a mapping table.
- Gap and Decision ids are generated by Auto (`{timestamp}-{random}`, like
  revision ids), never by Memo.
- Auto fields are stored as front matter properties; free text (question,
  rationale) is also rendered in the body for readability.

## Format

Entries are stored under the `auto` namespace, named after the plan and the id:

```text
auto/gap:{plan}+{id}        eg. auto/gap:release_notes+20261105T101230Z-3f9a
auto/decision:{plan}+{id}
```

The plan id is written as a Memo topic (`-` replaced by `_`).

```markdown
---
identity: auto:release-notes/gap/20261105T101230Z-3f9a
plan: auto:release-notes
gap_kind: approval
status: Open
revision: 20261105T101230Z-3f9a
raised_by: auto:release-notes/run/summarize-changes-20261105T1012-01
needed_by: [auto:release-notes/task/publish]
subjects:
  - ref: auto:release-notes/task/summarize-changes/definition
    digest: sha256:9f2c…
options: [approve, reject]
---
# Approve the release notes summary

Question text, as raised.
```

The Gap `kind` (`input`, `information`, `decision`, `approval`) is stored as
`gap_kind`, so it is not confused with the Memo kind (`gap`), which is the
entry type.

## Operations

The integration implements the Gap operations of the plan (`GapRaise`,
`GapList`, `GapDecide`, `GapDismiss`) and repair lookups with Memo operations:

| Auto need | Memo operation |
|---|---|
| Create a Gap or Decision | `EntryCreate`, asserting the identity is new |
| Update Gap status | `EntryEdit`, with the expected revision |
| Gaps of a plan | `EntryList` filtered by kind `gap` and `meta.plan` |
| Resolve a `memo:{ref}` transclusion | `EntryRead`, returning content and revision |

## Rules

- *Access*: Auto reads and writes Memo through the integration only, never by
  editing `.memo/` files directly.
- *Digests*: for Auto references, the digest is computed by Auto (see Plan
  digest). For Memo entries (`memo:{ref}`), the digest is the Memo revision,
  obtained from a read and never computed by Auto.
- *Write order*: Memo is written before the plan journal (see Plan rules).
  Resolving a gap writes two entries, the Decision then the Gap status; Memo
  gives no atomicity across them.
  Recording a decision without a gap writes one entry, without a `gap`
  property and with its `source`.
- *Repair*: in addition to the plan repair rules, a Decision whose Gap is
  still `Open` completes the Gap update before the journal is appended.
- *Safe writes*: every update carries the expected Memo revision; a stale
  write is re-read and reconciled, never overwritten.
- *Record for agents*: Gap and Decision entries are ordinary Memo entries;
  agents cite Decisions as record (see [Memorisation](spec-010-memorisation.md#decisions)).

## Out of Scope

- Learning records and their mapping (see [Memorisation](spec-010-memorisation.md))
- Storage of plans, tasks and runs, which stay in the plan directory (see Plan)
- Memo primitives: identity, revisions, front matter, queries (see Memo specs)
